SPSC RING BUFFER: MECHANICAL DESIGN

[ STABLE ] LOCK-FREE WAIT-FREE ALIGNAS(64) NO DIVISION / BITWISE INDEXING

The volt::SPSCQueueStatic is a fixed-capacity, single-producer single-consumer wait-free ring buffer. It provides concurrent lock-free synchronization across two dedicated processor cores without operating system kernel arbitration, mutex locks, or atomic comparison-and-swap (CAS) retry loops.

64B CACHE GRANULARITY & MESI BUS TRAFFIC

Modern x86-64 microarchitectures transfer memory between L1/L2/L3 caches and main memory in fixed 64-byte cache lines. When two separate CPU cores concurrently read and write independent variables residing within the same 64-byte boundary, hardware cache-coherency protocols (MESI / MOESI) force cross-core invalidation broadcasts. A store by Core 0 to tail_ invalidates Core 1's copy of head_, provoking severe false sharing pipeline stalls.

MECHANICAL ISOLATION: ALIGNAS(64) PADDING

By declaring alignas(64) (or alignas(std::hardware_destructive_interference_size)), the compiler forces head_ and tail_ onto discrete 64-byte cache lines. Each core retains exclusive ownership of its active line in the Modified (M) or Exclusive (E) state, generating zero invalidation bus traffic across the interconnect.

PANEL STRIP 1 // CACHE LINE ISOLATION & FALSE SHARING EXACT BYTE-OFFSET VECTOR DIAGRAM
PANEL 1.A // UNPADDED STRUCT (64B CACHE LINE) COLLISION: MESI INVALIDATION

Both head_ (8B) and tail_ (8B) reside within identical 64-byte cache line 0x00 - 0x3F. Concurrent stores by Core 0 trigger continuous MESI invalidation ping-ponging on Core 1.

MICROARCHITECTURAL PENALTY: Core 0 store transitions line to Modified (M), transmitting an invalidation message over interconnect. Core 1 suffers an L1 D-Cache miss and pipeline stall.
PANEL 1.B // CACHE-ALIGNED STRUCT (128B SPLIT) ISOLATION: 0 INVALS

alignas(64) forces head_ and tail_ across a 64-byte boundary. 56 bytes of halftone-shaded padding isolate each cursor into its own cache line.

VERIFIED GUARANTEE: Core 0 writes exclusively to Cache Line 1 (0x40), while Core 1 reads exclusively from Cache Line 0 (0x00). False sharing is mathematically eliminated.
PANEL STRIP 2 // C++23 TRY_PUSH() & ASSEMBLY INSPECTOR
MECHANICAL IDENTITY & HARDWARE MAPPING
BITWISE WRAP-AROUND: (head + 1) & mask_ / (tail + 1) & mask_
When capacity $C$ is constrained to a power-of-two ($2^k$, verified by std::has_single_bit(Cap)), mathematical modulo $(x \pmod{2^k})$ is identical to bitwise AND $(x \ \& \ \text{mask\_})$ where $\text{mask\_} = \text{Capacity} - 1$. In x86-64 assembly, and reg, 1023 executes in 1 CPU cycle with 0.25 cycle reciprocal throughput, bypassing the non-pipelined integer division unit (idiv), which incurs 10 to 35 CPU cycles of latency and stalls execution port 0.
volt/Containers/SPSCQueueStatic.hpp C++23 STANDARD 
template <typename T, std::size_t Cap>
    requires (Cap > 0 && std::has_single_bit(Cap))
class SPSCQueueStatic {
public:
    static constexpr std::size_t Mask = Cap - 1;

    bool push(const T& value) {
        const auto tail = tail_.load(std::memory_order_relaxed);
        if (tail - cached_head_ == Cap) {
            cached_head_ = head_.load(std::memory_order_acquire);
            if (tail - cached_head_ == Cap)
                return false; // Buffer full
        }

        // Power-of-two bitwise modulo (1 cycle latency)
        std::construct_at(ptr(tail & Mask), value);

        // Release store publishes element to consumer
        tail_.store(tail + 1, std::memory_order_release);
        return true;
    }

    bool pop(T& out) {
        const auto head = head_.load(std::memory_order_relaxed);
        if (cached_tail_ == head) {
            cached_tail_ = tail_.load(std::memory_order_acquire);
            if (cached_tail_ == head)
                return false; // Buffer empty
        }
        T* element = ptr(head & Mask);
        out = std::move(*element);
        std::destroy_at(element);
        head_.store(head + 1, std::memory_order_release);
        return true;
    }
private:
    alignas(64) std::atomic<std::size_t> head_{0};
    alignas(64) std::atomic<std::size_t> tail_{0};
    alignas(64) std::size_t cached_head_{0};
    alignas(64) std::size_t cached_tail_{0};
};
ASSEMBLY DISASSEMBLY (x86-64 -O3)
x86 TSO ORDERING & COMPILER BARRIERS: On x86-64 hardware, Total Store Order (TSO) guarantees that standard mov instructions already provide acquire semantics on reads and release semantics on writes without hardware mfence or lock instructions. However, C++ memory_order_acquire and memory_order_release arguments are still strictly required because they stop the compiler from reordering loads and stores across the atomic operation at compile time.

// Multi-million item concurrent stress test validating monotonic ordering
inline StaticStressResult run_static_stress(usize item_count) {
    volt::SPSCQueueStatic<std::uint64_t, 1024> q;
    std::atomic<std::uint64_t> produced{0}, consumed{0}, mismatches{0};

    std::thread producer([&] {
        for (std::uint64_t i = 0; i < item_count; ++i) {
            while (!q.push(i)) { std::this_thread::yield(); }
            produced.fetch_add(1, std::memory_order_relaxed);
        }
    });

    std::thread consumer([&] {
        std::uint64_t expected = 0;
        while (expected < item_count) {
            std::uint64_t value = 0;
            if (!q.pop(value)) { std::this_thread::yield(); continue; }
            if (value != expected) {
                mismatches.fetch_add(1, std::memory_order_relaxed); // MUST REMAIN ZERO
            }
            ++expected;
            consumed.fetch_add(1, std::memory_order_relaxed);
        }
    });

    producer.join();
    consumer.join();
    return { produced.load(), consumed.load(), mismatches.load() };
}

CRITICAL LIMITATIONS & MECHANICAL CONSTRAINTS: SPSC QUEUES
  • Strictly Single-Producer Single-Consumer: SPSCQueueStatic and FastRingBuffer are strictly designed for exactly one writer thread and one reader thread. Calling push() or pop() concurrently from multiple threads without external locks causes uncoordinated index writes, data corruption, and Undefined Behavior.
  • Compile-Time Power-of-Two Requirement: Capacity Cap must strictly satisfy std::has_single_bit(Cap). Non-power-of-two capacities are rejected at compile time via template constraints.
  • Fixed Non-Growing Storage: The ring buffer storage is fixed at instantiation. When the queue fills, push() immediately returns false without dynamically allocating or expanding. Callers must handle backpressure.

MEMORY ALLOCATORS: LINEAR, POOL & BUDDY

LINEAR [STABLE] POOL [STABLE] BUDDY [EXPERIMENTAL] BUMP-POINTER O(1) INTRUSIVE FREELIST

General-purpose dynamic memory allocators (such as malloc, free, or ptmalloc) maintain complex internal structures: segregated size classes, free-list linked lists with pointer-chasing traversals, per-chunk boundary tags (8-16 bytes overhead per allocation), and multithreaded lock contention. Volt provides purpose-built, hardware-conscious allocators.

LINEAR ARENA ALLOCATOR O(1) BUMP

MECHANICS: Memory is allocated sequentially along a pre-reserved contiguous span. Allocation is a single alignment addition and pointer bump. Deallocation is strictly $O(1)$ by resetting current_ = begin_ or rewinding to a saved Marker.

FIXED-SLOT POOL ALLOCATOR INTRUSIVE FREELIST

MECHANICS: Fixed-capacity slots of uniform size SlotSize = max(sizeof(T), sizeof(uint32_t)). Free slots embed the integer index of the next available slot directly inside the unused memory chunk. Zero external overhead; $O(1)$ pop and push onto the embedded singly-linked list.

BUDDY ALLOCATOR: BINARY TREE POWER-OF-TWO SPLIT & COALESCE XOR BUDDY SEARCH

BITWISE BUDDY XOR: When a block of size $2^k$ is freed, its buddy address is computed in a single CPU instruction: offset ^ (1 << order). If the buddy is also marked free, they coalesce instantly into a block of order $k+1$, cascading upwards to combat external heap fragmentation.

volt/memory/LinearAllocator.hpp C++23 STANDARD 
#pragma once
#include <bit>
#include <cstddef>
#include <cstdint>
#include <cassert>

namespace volt {
    class LinearAllocator {
    public:
        using Marker = std::byte*;

        LinearAllocator(void* memory, std::size_t size) noexcept
            : begin_(static_cast<std::byte*>(memory)),
              current_(begin_),
              end_(begin_ ? begin_ + size : nullptr) {}

        void* allocate(std::size_t size, std::size_t alignment = alignof(std::max_align_t)) noexcept {
            assert(alignment > 0 && std::has_single_bit(alignment));

            const auto current = reinterpret_cast<std::uintptr_t>(current_);
            const auto aligned = (current + alignment - 1) & ~(alignment - 1);
            const auto end = reinterpret_cast<std::uintptr_t>(end_);

            if (aligned > end || size > end - aligned)
                return nullptr;

            current_ = reinterpret_cast<std::byte*>(aligned + size);
            return reinterpret_cast<void*>(aligned);
        }

        void reset() noexcept { current_ = begin_; }
        Marker mark() const noexcept { return current_; }
        void rewind(Marker marker) noexcept {
            assert(marker >= begin_ && marker <= current_);
            current_ = marker;
        }
    private:
        std::byte* begin_{nullptr};
        std::byte* current_{nullptr};
        std::byte* end_{nullptr};
    };
}
volt/memory/PoolAllocator.hpp C++23 STANDARD 
#pragma once
#include <algorithm>
#include <cassert>
#include <cstdint>
#include <memory>

namespace volt {
    template <typename T, std::size_t Capacity>
    class PoolAllocator {
        using Index = std::uint32_t;
        static constexpr Index InvalidIndex = ~Index{0};
        static constexpr std::size_t SlotSize = std::max(sizeof(T), sizeof(Index));
        static constexpr std::size_t SlotAlign = std::max(alignof(T), alignof(Index));
    public:
        PoolAllocator() noexcept {
            for (Index i = 0; i < Capacity - 1; ++i)
                *reinterpret_cast<Index*>(slot_ptr(i)) = i + 1;
            *reinterpret_cast<Index*>(slot_ptr(Capacity - 1)) = InvalidIndex;
        }

        T* allocate() noexcept {
            if (free_head_ == InvalidIndex) return nullptr;
            Index idx = free_head_;
            free_head_ = *reinterpret_cast<const Index*>(slot_ptr(idx));
            ++size_;
            return reinterpret_cast<T*>(slot_ptr(idx));
        }

        void deallocate(T* ptr) noexcept {
            assert(ptr != nullptr);
            Index idx = slot_index(ptr);
            *reinterpret_cast<Index*>(slot_ptr(idx)) = free_head_;
            free_head_ = idx;
            --size_;
        }
    private:
        alignas(SlotAlign) std::byte storage_[Capacity * SlotSize];
        Index free_head_{0};
        std::size_t size_{0};
        std::byte* slot_ptr(Index idx) noexcept { return storage_ + idx * SlotSize; }
        Index slot_index(const T* ptr) const noexcept {
            return static_cast<Index>((reinterpret_cast<const std::byte*>(ptr) - storage_) / SlotSize);
        }
    };
}

CRITICAL LIMITATIONS & MECHANICAL CONSTRAINTS: MEMORY ALLOCATORS
  • LinearAllocator Does Not Call Destructors: reset() strictly sets current_ = begin_ in $O(1)$ time. Destructors for non-trivially destructible types are NOT automatically invoked. Callers are responsible for manual destructor invocation, or should restrict arena usage to POD / trivially-destructible scratch memory (e.g. per-frame rendering buffers).
  • Monolithic Lifecycle: Memory allocated from LinearAllocator cannot be freed individually. Reclaiming memory requires a complete reset() or rewinding to a previously saved Marker.
  • PoolAllocator Uninitialized Storage: Storage is allocated as raw aligned bytes. allocate() returns uninitialized memory; callers must use placement new (std::construct_at) if constructing non-trivial types.
  • PoolAllocator Capacity Constraint: Capacity must be greater than zero and compile-time fixed. Exceeding capacity causes allocate() to return nullptr.
  • BuddyAllocator Experimental Status: BuddyAllocator is currently undergoing architectural revision; internal fragmentation occurs when allocation sizes fall just above power-of-two boundaries.

CACHE-CONSCIOUS CONTAINERS: SPATIAL LOCALITY

[ STABLE ] FASTRingBuffer SMALLVECTOR SBO NO DIVISION / BITWISE INDEXING

CPU hardware stream prefetchers monitor memory access stride patterns. Traversing node-based pointer chains (such as std::list or std::map) causes high L1/L2 miss rates due to scattered heap addresses. Volt structures guarantee contiguous layout and high spatial locality.

FASTRingBuffer: ZERO-DIVISION CIRCULAR ARRAY

In volt::FastRingBuffer<T, Cap>, push and pop operations calculate element addresses with index & (Cap - 1). Because capacities are static powers of two, modulo operations compile to a single 1-cycle bitwise and instruction. While push() includes a branch to check if the buffer is full (if (full()) return false;), it eliminates integer division instructions entirely.

SmallVector: SMALL BUFFER OPTIMIZATION (SBO)

volt::SmallVector<T, N> embeds an inline array of $N$ contiguous elements directly into the struct's own footprint. Collections with $N$ or fewer elements execute zero dynamic heap allocations. Memory prefetchers load both container metadata and payload in a single cache line access.

volt/Containers/FastRingBuffer.hpp NO DIVISION / BITWISE INDEXING 
template <typename T, std::size_t Cap>
    requires (Cap > 0 && std::has_single_bit(Cap))
class FastRingBuffer {
public:
    static constexpr std::size_t Mask = Cap - 1;

    bool push(const T& value) {
        if (full()) return false;
        std::construct_at(ptr(tail_ & Mask), value);
        ++tail_;
        return true;
    }

    void pop() {
        assert(!empty());
        std::destroy_at(ptr(head_ & Mask));
        ++head_;
    }

    [[nodiscard]] constexpr bool full() const noexcept { return (tail_ - head_) == Cap; }
    [[nodiscard]] constexpr bool empty() const noexcept { return head_ == tail_; }
private:
    alignas(alignof(T)) std::byte storage_[Cap * sizeof(T)];
    std::size_t head_{0};
    std::size_t tail_{0};
    T* ptr(std::size_t index) noexcept { return reinterpret_cast<T*>(storage_ + index * sizeof(T)); }
};
CRITICAL LIMITATIONS & MECHANICAL CONSTRAINTS: CONTAINERS
  • SmallVector Heap Fallback: SmallVector<T, N> only avoids heap allocations while size $\le N$. Exceeding $N$ elements causes heap allocation via std::allocator, sacrificing stack locality. Large values of $N$ will bloat the stack footprint.
  • FastRingBuffer Single-Threaded Contract: FastRingBuffer does NOT use atomics or memory barriers; it is strictly intended for single-threaded usage. For multi-threaded lock-free communication, use SPSCQueueStatic.
  • RingBuffer Overwrite Behavior: RingBuffer<T, Cap> implements circular sliding-window semantics: pushing to a full ring buffer silently overwrites the oldest element. If loss of old data is unacceptable, check full() before pushing or use FastRingBuffer.

DATA-ORIENTED ECS: ARCHETYPES & COLUMN STORAGE (EXPERIMENTAL)

[ EXPERIMENTAL / IN PROGRESS ] STRUCT-OF-ARRAYS (SoA) SWAP-AND-POP O(1) 64-BIT BITMASKS

The Volt Entity Component System (ECS) implements a modern Archetype-based storage architecture. Rather than storing components scattered in heap nodes or polymorphic entity wrappers, entities sharing identical component combinations reside in contiguous, column-oriented archetype tables.

CONTIGUOUS COLUMN STORAGE (SoA)

Components reside in contiguous column vectors managed via Archetype::register_column<T>() and Archetype::get_column<T>(). This Struct-of-Arrays (SoA) layout preserves spatial locality. Multi-component join queries (e.g. view<Transform, Velocity>()) are planned future work.

SWAP-AND-POP DELETION IN O(1)

When an entity is destroyed or transitions archetypes, its row is swapped with the trailing row: data[row] = std::move(data.back()); data.pop_back();. Row deletion remains strictly $O(1)$ without memory holes.

volt/ECS/Archetype.hpp DATA-ORIENTED C++23 
template<typename T>
class ComponentColumn : public IComponentColumn {
public:
    std::vector<T> data;

    void swap_pop(std::size_t row) override {
        assert(row < data.size());
        if (row + 1 < data.size()) {
            data[row] = std::move(data.back());
        }
        data.pop_back();
    }
};
CRITICAL LIMITATIONS & MECHANICAL CONSTRAINTS: ARCHETYPE ECS
  • Prototype Status (No Query Views Yet): The ECS implementation is an experimental storage engine. High-level entity querying iterators (e.g. view<A, B>()) and multithreaded system dispatchers are in progress; users currently access column vectors directly via get_column<T>().
  • Mandatory Column Registration: All component types must be registered upfront using Archetype::register_column<T>() before entities are instantiated. Adding new component columns to an archetype at runtime requires reallocation.
  • Row Reordering on Deletion: swap_pop(row) swaps the target entity row with the trailing element in each column vector. This maintains $O(1)$ removal without memory holes, but reorders the trailing entity's row index, requiring external entity-to-row lookup synchronization.

CONCURRENCY & JOB SYSTEMS (EXPERIMENTAL)

[ EXPERIMENTAL ] THREAD POOL CENTRAL WORK QUEUE TASK BARRIER

Volt includes a lightweight thread_pool designed for asynchronous task dispatch and completion barrier synchronization (wait()). The implementation relies on a centralized mutex-guarded FIFO task queue (std::queue<Task>) with worker wake-up coordinated via std::condition_variable.

volt/JobSystems/ThreadPool.hpp C++23 CONCURRENCY 
class thread_pool {
public:
    explicit thread_pool(std::size_t worker_count) {
        workers_.reserve(worker_count);
        for (std::size_t i = 0; i < worker_count; ++i) {
            workers_.emplace_back([this] { WorkerLoop(); });
        }
    }

    template<typename F, typename... Args>
    void submit(F&& func, Args&&... args) {
        {
            std::lock_guard lock(mutex_);
            if (stopping_) return;
            tasks_.emplace([func = std::forward<F>(func), ...args = std::forward<Args>(args)]() mutable {
                std::invoke(func, std::forward<decltype(args)>(args)...);
            });
            ++pending_count_;
        }
        cv_.notify_one();
    }
};
CRITICAL LIMITATIONS & MECHANICAL CONSTRAINTS: THREAD POOL
  • Centralized Mutex Contention: All worker threads contend on a single std::mutex to pop tasks from the shared queue. While efficient for coarse workloads, dispatching hundreds of thousands of microscopic tasks will induce severe lock contention and tail latency spikes.
  • No Work-Stealing Yet: The current pool lacks per-worker work-stealing deques (such as Chase-Lev). Work-stealing is active future work (see Chapter 08).
  • OS Thread Affinity Not Hardcoded: ThreadPool.hpp does not pin worker threads to physical CPU cores; thread scheduling and migration are handled by the host OS kernel scheduler.

ROADMAP & NON-GOALS

GROUNDED ROADMAP 3 CONCRETE TARGETS SCOPED BOUNDARIES

Volt is a focused systems runtime built to solve concrete game-engine and low-latency systems bottlenecks. Rather than speculative feature inflation, the roadmap is restricted to three active development targets that directly improve existing primitives.

TARGET // 01 ACTIVE PROTOTYPE

CHASE-LEV LOCK-FREE WORK-STEALING DEQUE

OBJECTIVE: Replace thread_pool's centralized std::mutex task queue with per-worker Chase-Lev deques.

  • [x] Single-producer LIFO fastpath for owner worker thread
  • [ ] Lock-free CAS FIFO steal path for remote idle workers
  • [ ] Benchmark throughput under 100k micro-tasks vs mutex baseline
BENEFIT: Eliminates thread contention on fine-grained task dispatch
TARGET // 02 DESIGN PHASE

ARCHETYPE ECS QUERY VIEWS (Registry::view<T, U>)

OBJECTIVE: Add multi-component join iterators that yield contiguous spans over matching archetype columns.

  • [ ] Archetype graph transitions when adding/removing components
  • [ ] Zero-allocation view iterator matching component bitmasks
  • [ ] Cache miss profiling during 100,000 entity transform/velocity updates
BENEFIT: Ergonomic, contiguous SoA multi-component systems iteration
TARGET // 03 PLANNED

THREAD-SAFE SLAB ALLOCATOR WITH LOCAL MAGAZINES

OBJECTIVE: Extend PoolAllocator with thread-local object magazines (Bonwick slab model) to avoid locks.

  • [ ] Thread-local magazine exchange on depletion/overflow
  • [ ] Shared central slab depot backed by virtual memory pages
  • [ ] Multi-threaded churn benchmark vs standard new/delete
BENEFIT: Scalable fixed-size allocations across arbitrary thread counts

ARCHITECTURAL BOUNDARIES EXPLICIT NON-GOALS FOR VOLT

To maintain extreme mechanical simplicity, predictable memory layouts, and zero bloat, the following areas are strictly out-of-scope:

  • NO General-Purpose Malloc Replacement: Volt does not aim to replace general-purpose heap managers like jemalloc or mimalloc. It focuses exclusively on scoped lifecycles (linear frame arenas and fixed-size object pools).
  • NO Coroutine / Asynchronous I/O Framework: Volt is not an async runtime like Boost.Asio or libuv. Network sockets, file I/O, and complex cooperative multitasking are non-goals.
  • NO MPMC Multi-Producer Queues: Multi-producer multi-consumer queues incur massive CAS contention and complex memory reclamation (EBR/hazard pointers). Volt's concurrent queues remain strictly Single-Producer Single-Consumer (SPSC) by design.
  • NO Polymorphic Object Hierarchies: Zero virtual methods in hot paths; all container operations rely on static compile-time polymorphism and explicit hardware data layout.
